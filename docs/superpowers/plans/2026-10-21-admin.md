# Admin Module Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An opt-in `admin` module (`admin.Register(ctx, a, cfg)`) with console users, fixed roles, TOTP, an audit log written in the same transaction as each change, player/bet/limit views, limit changes, identity unlink, ledger-backed balance adjustments with approval, brand views declared in Go (`adm.View`), and an embedded white-label Refine UI.

**Architecture:** Platform packages gain small additive hooks first (`app.Serve`, `app.Bets`, `ledger.Adjust`, `gameconfig` tx writes, `auth` tx unlink, `fairness.PairsOf`). Then `admin/` owns its tables (goose table `goose_admin`), sqlc queries in `admin/internal/store`, a JSON API on its own listener, and serves `admin/ui/dist` via `go:embed`. The UI is Vite + React + Refine + shadcn/ui in `admin/ui`, built output committed.

**Tech Stack:** Go 1.27, pgx v5, sqlc, goose, `golang.org/x/crypto/argon2`; Node 22 + pnpm, Vite, React, TypeScript, `@refinedev/core`, `@refinedev/react-router`, shadcn/ui, Tailwind; Playwright for the e2e smoke.

**Spec:** `docs/superpowers/specs/2026-10-21-admin-design.md`

## Global Constraints

- Money is `int64` minor units; UI parses decimal strings to `int64`, never floats.
- No balance change except `Ledger.Adjust` with transfer ID `{nsAdjust << 32, adjustmentID}`, `nsAdjust = 6`. No app-side balance checks.
- New ledger constants are appended: `kindAdjust` after `kindRewards`, account code `codeAdjust uint16 = 17`, transfer code `codeAdjustment uint16 = 18`. Never change existing ones.
- Never return, log or audit an unrevealed server seed. The SQL behind `fairness.PairsOf` doesn't select `server_seed_enc` for unrevealed rows.
- Every admin write: one Postgres transaction containing the change and its `admin_audit` row. The audit table has no UPDATE/DELETE query.
- Admin runs only on `Config.Addr` (required, no default) via `App.Serve`; never on `App.HTTP`.
- Writes require header `X-Admin: 1` and `Origin` == `Config.Origin`. Cookie `gamify_admin`: `HttpOnly; Secure; SameSite=Strict; Path=/`.
- Sessions: idle 30 min, absolute 12 h. Lockout: 5 failed logins per email in 15 min → refused for 15 min.
- Roles `owner`, `operator`, `support`, `viewer`; permission table exactly as in the spec. Brand permissions come only from `Config.Perms`; owners hold every permission.
- Brand view actions run in the admin's transaction and never call the ledger.
- argon2id: memory 19456 KiB, time 2, threads 1, salt 16 bytes, key 32 bytes, PHC string format.
- TOTP: RFC 6238, SHA-1, 6 digits, 30 s step, accept ±1 step, refuse a step ≤ the last accepted one.
- TOTP secrets sealed with AES-256-GCM under `Config.TOTPKey` (32 bytes), AAD `admin-totp:<admin id>`.
- Pagination: keyset `before`/`limit` (default 50, max 100), response `{"items": [...], "next": <id or null>}`.
- Errors: `{"code": "<snake_case>", "message": "…"}` with 4xx status.
- sqlc for every query; generated code in `admin/internal/store`; add the `sqlc.yaml` entry.
- Additions only: no exported signature changes, no edits to committed migrations. Every user-visible change goes in `CHANGELOG.md` under Unreleased.
- The repo has no commits yet. No commit steps: the user commits.
- macOS: `CGO_LDFLAGS=-Wl,-ld_classic`. Integration tests need `TEST_DATABASE_URL` (and `TEST_TB_ADDRESS` for TigerBeetle).

## Review Focus

1. A request that changes a limit to loosen a code cap (max_bet above `Game.MaxBet`) must be refused with 400 and leave no audit row (Task 3 `TestSetLimitRefusesLoosen`, Task 9 `TestLimitWriteAudited`).
2. A double-clicked adjustment (same idempotency key, two concurrent requests) must create one row and one transfer (Task 10 `TestAdjustConcurrentSameKey`).
3. An adjustment amount entered as `"1.005"` for a 2-decimal currency, `"-0"`, `"1e3"` or `" 12"` must be refused by the UI parser, not rounded (Task 14 `parseAmount.test.ts`).
4. A session of a user whose role was lowered must lose the old role's permissions on the next request (Task 9 `TestRoleChangeKillsSessions`).
5. A brand action whose `Run` panics after writing must leave no change, no audit row and a server still serving (Task 11 `TestViewActionRollsBack`).
