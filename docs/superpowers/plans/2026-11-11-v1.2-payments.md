# v1.2 Payments Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Users deposit into and withdraw out of real-money currencies through brand-written
`Receiver`s and `Sender`s, registered in a new `payments` module, with an admin console for both.
First task: the pool-starvation fix carried over from v1.1.

**Architecture:** The ledger gains a `Withdrawable` switch, an `outflow` system account and
pending-transfer withdrawals (`Withdraw` / `PostWithdraw` / `VoidWithdraw`). `payments` owns its
tables, records a row before every ledger move (row ID = transfer ID), drives withdrawals through a
state machine with a lease-based worker and the reconciler, and calls brand code only outside
transactions. `payments/paymentsadmin` adds the console pages, as `matchmakingadmin` does.

**Tech Stack:** Go, pgx/v5, sqlc, goose (via `a.Migrate`), TigerBeetle 0.16.46 / Postgres ledger
drivers, Centrifugo (`realtime`), the admin `View` API.

**Spec:** `docs/superpowers/specs/2026-11-11-payments-design.md`

## Global Constraints

- Additive only (v1 is tagged): no committed migration edited, no exported API broken; new
  `CHANGELOG.md` section under Unreleased with upgrade notes. Release tag `v1.2.0` only on the
  owner's go.
- Money: `int64` minor units, never floats. No app-side balance checks: the driver refuses
  overdrafts.
- Every ledger move: write the row first, move money with the row ID. Never random IDs.
- `ledgertest` must pass on Postgres **and** TigerBeetle; never weaken a case.
- User identity only from the connection (`realtime.JSON`'s `userID`), never from a payload.
- Every money-moving RPC carries `idem_key`.
- sqlc for every query; generated code in `payments/internal/store`; run `sqlc generate`.
- No hard-coded policy: limits, fee, approval thresholds are config (Go default, console override).
- Never call a `Sender` or `Receiver` while holding a DB transaction or a row lock.
- Platform client error codes: payments uses 1040–1049 (below the games' 1100).
- macOS builds: `CGO_LDFLAGS=-Wl,-ld_classic`.

## Review Focus

1. A `Send` that times out or errors, then a crash: the withdrawal is never voided until the sender
   says `Failed` (no "paid on-chain and refunded"). Test in Task 6.
2. Two concurrent `payments.withdraw` calls that together pass the daily cap or the balance: one is
   refused; the cap is checked under a per-user lock. Test in Task 5.
3. Withdrawing into the welcome grant: refused by the ledger, so play-only money can't be cashed
   out. Test in Task 2.
4. The same deposit reported twice (webhook redelivery, two instances polling the chain): credited
   once. Test in Task 4.
5. The same console user giving both approvals on a withdrawal above the second-approval amount:
   refused. Test in Task 8.

### Task 6: Sending and settling withdrawals

**Files:**
- Create: `payments/send.go`
- Test: `payments/send_test.go`

**Interfaces:**
- Consumes: `Sender`, `ledger.PostWithdraw` / `VoidWithdraw`, `pushWithdrawal`.
- Produces:
  - `func (s *Service) advance(ctx context.Context, id int64) error` — the only place that calls
    `Send`/`Status` and the ledger for a withdrawal.
  - `s.tick` (Loop) and `s.Reconcile` both claim due rows and call `advance`.

State rules (the spec's money-safety rule, exact):

| Row | Action | Outcome |
|---|---|---|
| `approved` | claim lease, set `sending`, commit, `Send` | `Paid` → `paid`; `Failed` → `failed`; `Pending` or error → stays `sending` |
| `sending` (lease expired) | claim lease, `Status` | `Paid` → `paid`; `Failed` → `failed`; `Unknown` → `Send` again (same ID); `Pending` or error → stays `sending` |
| `paid`, not settled | `PostWithdraw(amount, fee)` | `settled = true` |
| `rejected`/`cancelled`/`failed`, not settled | `VoidWithdraw` | `settled = true` |

Claiming = `UPDATE … SET lease_until = now() + Lease WHERE id = $1 AND (lease_until IS NULL OR lease_until < now()) RETURNING`;
no transaction is open during `Send`/`Status`.

  - `TestSendFailedRefunds`: `Failed` → `failed`, balance restored.
